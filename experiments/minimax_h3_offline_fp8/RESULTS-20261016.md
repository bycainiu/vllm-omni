# MiniMax H3 离线 FP8 权重与 5090 对照结果（2026-10-16）

## 实验范围

- 源码副本：`vllm-omni-baseline`，commit `c2ba8e7`，仅修改当前实验副本。
- BF16 原始模型：5090 主机 `/mnt/data/MiniMax-H3/Ref2VA`，转换与服务时均以只读方式挂载。
- FP8 候选权重：5090 主机 `/home/niuzifan/h3-5090-bench/variants/offline-fp8-20261016/artifacts/Ref2VA-FP8-offline-20261016`。
- 因 GPU 4–7 持续被外部任务占用，本次完成的是 GPU 0–3 上的匹配对照：TP4×USP1、文本编码器 TP4、VAE patch=4。没有运行目标 8×5090 TP4×USP2 的正式对照。

## 1. 离线转换与 CPU 审计

转换在 `vllm/vllm-omni:nightly` 容器中执行，设置 `CUDA_VISIBLE_DEVICES=`，且 `torch.cuda.is_available()` 为 `False`；13 个 transformer shard 用时 232.834 秒。

- 对 50 个 DiT block 中的 200 个融合线性矩阵做 E4M3 per-output-channel 权重量化，共 19,267,584,000 个参数。
- 每行 scale 为 `max(abs(weight_row))/448`，存为 FP32 `<module>.weight_scale`；推理激活由运行时按 token 动态量化。
- 目标权重由 BF16 的 38,535,168,000 bytes 降为 FP8 的 19,267,584,000 bytes；加上 3,046,400 个 FP32 scale（12,185,600 bytes），净减少约 19.26 GB（17.94 GiB）。完整转换后 transformer shard 总大小为 47,025,107,720 bytes。
- AdaLN、condition projection、token refiner、final layer、文本编码器和 VAE 保持原 checkpoint 精度。
- CPU 审计遍历全部 200 个权重 dtype/shape 和 3,046,400 个 scale；抽查三个矩阵的权重相对 RMSE 为 2.6431%、2.6455%、2.6450%。这是权重量化误差，不是生成视频质量指标。
- 4 个针对 exporter、保留 BF16 张量、QKV scale 排列、FC1 scale 拆分的单元测试通过。

该导出遵循 vLLM 当前 ModelOpt FP8 checkpoint 读取约定，但没有调用 NVIDIA ModelOpt 的 `mtq.quantize` 导出器。

## 2. GPU 0–3 上的 BF16/FP8 单次匹配对照

两次都使用同一源码副本、固定 seed=1101、相同提示词/参考图、480×320、124 帧、24 fps、50 步、50 层 DLO 常驻、CPU offload 关闭、CUDNN attention、eager 模式和 PyTorch Profiler。BF16 服务读取原始模型；FP8 服务读取离线候选。为适配 4 卡，二者均使用 TP4×USP1、文本编码器 TP4、VAE patch=4。

| 指标 | BF16 原始权重 | 离线 FP8 | 观察 |
|---|---:|---:|---|
| API 结果 | HTTP 200 | HTTP 200 | 两次均成功生成 |
| 50 步进度条区间 | 72 s | 62 s | FP8 少约 10 s（−13.9%），仅表示去噪进度条区间 |
| Client E2E | 247.050 s | 262.191 s | FP8 本次慢 15.141 s（+6.13%） |
| `MiniMaxH3Pipeline.diffuse` 最慢 rank 区间 | 233.409 s | 250.014 s | FP8 本次慢约 7.11% |
| GPU 峰值显存（每卡，`nvidia-smi`） | 18,038 MiB | 13,518 MiB | FP8 少 4,520 MiB/卡，约 25.1% |
| 视频 | H.264，480×320，124 帧，5.1667 s | H.264，480×320，124 帧，5.1667 s | 容器与帧数一致 |
| 视频文件大小 | 2,378,767 bytes | 2,288,446 bytes | 编码后大小不能单独代表画质 |

对两支已经编码为 H.264 的输出逐帧比较，FFmpeg 汇总得到 SSIM All=0.926177、PSNR average=31.380640 dB。它们衡量的是 FP8 输出与 BF16 输出的相似度，不是与真实目标视频的画质误差。接触表上排为 BF16、下排为 FP8：[`video-comparison-contact.png`](../../results/video-comparison-contact.png)。

### PyTorch Profiler（rank 0）

下面是 profiler 的 `Self CUDA` 统计；异步操作可能重叠，这些值不能相加成端到端时间。BF16 `aten::mm` 与 FP8 `cutlass_scaled_mm` 的算子名称、shape 和调用数也不完全一一对应，适合定位路径，不足以单独宣称整体加速。

| 观察项 | BF16 | FP8 |
|---|---:|---:|
| `nccl:all_reduce`，7,800 calls | 39.839 s | 32.498 s |
| 矩阵乘算子 | `aten::mm`：13.584 s / 10,400 calls | `cutlass_scaled_mm`：6.672 s / 10,000 calls |
| cuDNN attention，2,600 calls | 3.837 s | 3.843 s |
| Pinned HtoD memcpy | 1.381 s / 151 calls | 1.014 s / 251 calls |
| FP8 动态 scale/requantize Triton kernel | — | 0.473 s / 10,000 calls |

Profiler 证实 FP8 线性层走到了 `cutlass_scaled_mm`，且对应矩阵乘的 rank-0 CUDA 统计更低；显存也显著下降。50 步进度条区间在 FP8 样例中短约 10 秒，但完整 `diffuse` 区间和 E2E 却较慢，说明这个单次样本中去噪核的收益没有传递到全链路。当前证据不足以归因于单一环节；需要更多重复样本，并结合分阶段时间拆分继续查 CPU/通信等待。

两轮 `host-state` 在 diffuse 窗口的 CPU busy 均约 99%，load1 均值约 229，CPU PSI some 均值约 0.36%；未观察到内存或 I/O PSI。该环境整体负载高，因此这组每变体一次的数字应视作调试观察值，不作为最终性能结论。
